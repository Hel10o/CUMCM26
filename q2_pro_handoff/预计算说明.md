# 第二问预计算说明

2026-09-11。**本文件及 `evidence/preflight_*` 是建模交接中的试算证据，尚不能作为第二问的最终答案。** 请先独立判断主文档中的模型，再比较这里的量级。

## 1. 实际运行了什么

从原附件读取环境，每 60 s 原始折点间作线性插值。从均匀初态 28 °C、2.55 kg/kg 开始，到 10800 s，全部物性采用附录 3。使用固定半径 0.02 m 的中截面径向有效模型；无显式蒸发潜热、骨架运动或收缩。继承换热系数 25 W/(m²·K)、等效传质系数 8×10⁻⁷ m/s。

试算没有导入第一问的 RHS。采用节点有限体积，面上分别调和平均导热系数和水分扩散系数，节点热容量保留在散度之外；温度和含水率联立积分。内部温度为摄氏度，指数中的温度转换为开尔文。

- 网格区间数：80、160、320，均包含轴心和真实表面节点。
- 方法：BDF，带完整相邻节点耦合的稀疏数值 Jacobian 结构。
- 容差：`rtol=1e-9`、`atol=1e-11`；最大步长 15 s；每 60 s 连续传递状态并重启，起始步长 0.001 s。
- 保存采样：0—10800 s，每秒一次，半径 0—2 cm，每 0.1 cm 一次。此处包含初值，因此数组为 10801×21；正式前 3 h Excel 应从第 1 s 开始。
- 三组试算均实际完成、无捕获到的运行警告；本机记录总用时约 12.76 s，不构成其他设备的性能承诺。
- 实际环境：Python 3.13.14、NumPy 2.3.5、SciPy 1.17.0。输入 SHA256 见 `evidence/preflight_results.json`。

## 2. 量级观察，不能直接冻结末位

下表仅摘要 320 区间试算，刻意少列小数，不是题目两张正式结果表。

| 时间 | 轴心温度 / °C | 表面温度 / °C | 轴心含水率 / kg/kg | 表面含水率 / kg/kg |
|---|---:|---:|---:|---:|
| 0.5 h | 32.19 | 35.41 | 2.550 | 1.649 |
| 3 h | 49.85 | 49.97 | 1.766 | 1.008 |

这说明在该有效模型下，前 3 h 热场已接近环境平台，水分仍有明显径向差异；3 h 时轴心含水率也已出现变化。它不证明真实药材一定遵循该轨迹，也不说明第三问何时达标。不能据此强迫其他合理闭合模型给出相同结果。

参数代入与局部尺度另存 `evidence/parameter_scales.json`，其中代表状态不是实测状态序列，特征时间也不是实际干燥完成时间。

## 3. 为什么还不能作为最终答案

对比两级网格，误差是采样点上的**级间差异**，不是相对精确解的严格误差界。

| 对比 | 全部逐秒输出最大温差 / K | 全部逐秒输出最大含水率差 / kg/kg | 60 个论文状态值中的最大温差 / K | 论文含水率最大差 / kg/kg |
|---|---:|---:|---:|---:|
| 80 → 160 | 7.9559×10⁻⁵ | 1.08656×10⁻² | 5.1517×10⁻⁵ | 4.6682×10⁻⁵ |
| 160 → 320 | 1.9881×10⁻⁵ | 4.97513×10⁻³ | 1.2927×10⁻⁵ | 1.1674×10⁻⁵ |

**关键发现：160 → 320 的最大含水率差出现在第 1 s 的真实表面。** 半小时间隔的论文值已经相近，但逐秒完整结果尚不能声称四位小数稳定。初始均匀水分与 Robin 边界在 t=0 的角点不相容，会产生很薄的早期表面层，必须单独分辨。Pro 应选择进一步细化、边界局部加密或其他经验证的方法，而不能仅因为 3 h 末态稳定就通过整个 Excel 的精度验收。

320 区间的累计离散平均含水率收支差约 5.33×10⁻¹⁵。它由同一 RHS 的边界通量增广积分得到，只是结构与积分一致性检查，**不是独立质量物理验证，更不是有效热方程的总焓守恒证明**。

本轮未完成：单独时间收敛、不同空间实现复算、所有正式输出的四位舍入核验、变容量热收支的独立轨迹求积、有限圆柱端部对照、界面/潜热闭合及参数敏感性比较、正式 Excel 导出与回读。这些要求已列入主交付说明，需由 Pro 对其最终选定模型完成。

## 4. 文件与重跑方法

从本包根目录执行：

```text
python -m pip install -r requirements-preflight.txt
python evidence/audit_inputs.py
python evidence/preflight_q2.py
```

第一条只安装试算依赖；输入审计脚本本身只使用标准库。两个脚本优先读取包内 `inputs/`，不依赖原项目或网络。试算会重新生成旁边的两个 JSON 和一个 NPZ，审计会重新生成 `data_contract_audit.json`；建议在解压副本中重跑，以保留交付时的原始记录和哈希清单。

`evidence/preflight_npz.npz` 仅保留 N=320 的未舍入采样轨迹，可使用 `numpy.load(..., allow_pickle=False)` 读取：

| 键 | 含义 |
|---|---|
| `scope` | 预计算限定说明 |
| `time_s`、`radius_cm` | 10801 个秒时刻、21 个半径 |
| `temperature_C` | 摄氏温度数组，形状 10801×21 |
| `moisture_dry_basis` | 干基含水率数组，形状 10801×21 |
| `average_T`、`average_C` | 各时刻圆柱控制体加权平均，形状 10801 |

80、160 区间未保留完整数组；其摘要及与相邻级的比较见 `preflight_results.json`。需要独立重算这些比较时，运行脚本即可，不要把缺失的粗网格数组描述为已随包保存。
