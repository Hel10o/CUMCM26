## 为什么 result2 拆成两个文件

题目要求第二问逐 1 s、径向每 0.1 cm 保存完整结果。全程工作簿为 206907 行 × 21 个位置 × 2 个物理量，
共 8,690,094 个数值；按现行序列化为 26.87 MB，与官方"支撑材料压缩包不超过 20 MB"冲突。

`xlsx` 本身是 deflate 压缩的容器，因此实测了三种独立序列化，均无法压到 20 MB 以内：

| 方案 | 实测大小 | 脚本 |
|---|---|---|
| 原始工作簿（对照） | 26.87 MB | — |
| 最小 ECMA-376 标记重写 | 28.83 MB | `slim_result2.py` |
| 共享字符串表重写 | 28.90 MB | `sst_probe.py` |

同一份数值若改为紧凑二进制数组只需约 2.4 MB（`int32×10000` 甚至 1.81 MB），说明超限是
xlsx 文本序列化的信息熵下界，不是标记冗余。因此本包按"模板工作簿 + 全程数组"提供，数值不删减：

- `results/result2.xlsx`：题面表 3、表 4 所用的前 3 h 网格（10801 行），模板格式
- `results/result2_全程轨迹_206907x21.npz`：烘干全程每个 1 s 的完整网格

两者数据一致：前 3 h 的 453,600 个温度与水分浓度值逐一相同，仅表头文字不同。

## 构建

```console
python build_package.py
```

脚本会重建全程数组、暂存 `stage/支撑材料/`、扫描身份信息、写 `evidence/package_report.json`
并断言 ZIP 不超过 20 MB。`stage/` 与探针输出不进入版本库。

本轮实际使用 `refresh_figures.py` 做仅图表与清单的打包刷新。它以提交
`dfe7b2911672deacdea62096fc409bcf04855fdf` 中原 ZIP 的 SHA-256 为入口检查，直接保留其数值文件，
不调用上述完整构建中的数组生成过程；当前 ZIP 已刷新，再运行该脚本会因基线哈希不同而停止，
防止把后续版本误作本次基线。它没有删除或移动任何暂存目录。

`slim_result2.py` 与 `sst_probe.py` 是上表两个压缩探针，只在 `out/` 写临时工作簿用于量体积；
两者都不产出交付文件，运行结果不作为交付证据保留。
